# Komova MCP resources

Connect an OAuth-capable MCP client to `https://api.komova.app/mcp`. Discovery advertises PKCE S256, curated client metadata (ChatGPT, Claude hosted chat, Codex and Hermes) and public Dynamic Client Registration for standards-compatible clients such as Claude Code, OpenCode and OpenClaw. Sign in and review Komova's consent before granting read or write access; write access includes deletion. Registered client names are self-declared. DeepSeek used within one of these applications is its model provider, not a separate verified MCP client. Refresh and revocation preserve the granted tool scopes; the current mobile app may display a generic MCP label for a new client while still revoking its exact connection. Protocol support does not establish that every vendor's real login has been tested.

The canonical URL for connecting Komova as a remote MCP server is `https://api.komova.app/mcp`. Each client must authorize its own connection; this resource contains no credentials.

The Komova plugin bundles the `komova-work` skill with the MCP connection. It also bundles the product guides and reference documentation for Komova capabilities, MCP tools and mobile views. Connecting the raw MCP URL does not install the skill or grant access: the client still needs authorization. The skill is not required to use these guides or tools.

The owner sees authorized apps in Settings → MCP Connections in the mobile app. There, the owner can revoke a connection after confirming it: Komova invalidates its access and refresh authorization without signing out of the mobile session. Disconnecting an app from Claude or ChatGPT alone does not confirm that its permission has been revoked in Komova.

Komova stores the owner's Projects, Items, Entries, Feedback and Forms. `list_projects` and `get_project` expose Projects and their current state; `list_project_items` and `get_item` do the same for Items. Each record has a UUID: names and titles are not unique identifiers. `add_project`, `change_project`, `add_item` and `change_item` create or update the corresponding records. `status_note` is free text shown at the bottom of the Project.

`DELETE /v1/projects/{project_id}` permanently deletes an owned Project and its current Items, Entries, Forms, answers, saved attachments and private drafts, Feedback, Reminders, goal proposals, schedules, activity, history and queued notifications, without moving Items into the inbox. The app requires a destructive confirmation. `delete_project(project_id)` exposes the same operation through MCP with write permission: obtain explicit user confirmation for the exact Project before calling and never automatically accept a client confirmation dialog. It returns only `deleted=true`. Other Projects, accounts and unrelated inbox Items remain. Historical handoff receipts, proposal metadata, dependency edges and events that reference removed records are also purged; current Items in surviving Projects remain, including Items created by those historical proposals. Missing or foreign Projects return `404`; real concurrent writes or notification deliveries return `409` with `project_changing`, leaving the aggregate unchanged for a deliberate retry. No deleted Project identifier or name is retained in a deletion tombstone; a generic account sync refreshes connected mobile clients. Backups and notification provider logs are outside this active-database deletion, and already delivered notifications cannot be recalled.

`list_project_items(scope="all")` includes Items with and without a Project; the latter have a null `project_id`. `scope="unassigned"` means no assignee (null `assigned_to_kind`), not no Project. The other `scope` values are `attention` and `future`. The `project_id` filter limits the list to a Project identified by UUID.

`list_reports` and `get_report` read Entries; `add_report` and `change_report` write them. `list_feedback` and `get_feedback` read human Feedback; acknowledgement and response operations are detailed in `komova://guides/feedback-and-handoffs`. Forms are read with `get_information_request`. The resources in this series describe the server contract; work decisions belong to the consumer.

`list_reminders(limit=100, before_id?)` returns at most 100 cards per call, using the last received ID to paginate; `get_reminder` reads one card. Both read short reminders created by agents. `add_reminder(text, target_kind, target_id, idempotency_key?)` creates one linked to an owner's Project, Item or Entry. The reminder appears immediately in Feed; it does not schedule future deliveries.

`get_change_snapshot` provides a bounded view of the current state and a `high_water_sequence`. `list_change_events` paginates retained changes from a global sequence per owner. `list_human_changes` and `list_agent_changes` filter by the change's **author**. The resource `komova://guides/change-events` details the cursor and retention.
