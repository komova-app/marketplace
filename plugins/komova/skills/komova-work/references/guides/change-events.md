# ChangeEvents and cursor

`ChangeEvent` records `sequence`, `kind`, `entity_id`, `operation`, `actor_kind`, destination, related Project, `change_set_id`, `payload_version`, JSON `payload`, date and human attention. `actor_kind` identifies the **author**, while `requires_human_attention` and `human_seen_at` describe a notification for the owner. `list_human_changes` filters changes made by a human; `list_agent_changes` filters changes made by agents. `list_change_events` accepts an explicit `actor_kind` or returns all auditable events. Technical invalidations (`event_role=signal`) do not appear in these lists.

`get_change_snapshot` returns a bounded current overview, `truncated` indicators per collection and a `high_water_sequence`. Entity tools expand any truncated collection. `list_change_events(after_sequence=high_water_sequence)` returns subsequent changes in ascending order. `next_cursor` identifies the page position; `has_more=true` means more pages remain. If `history_gap=true`, the requested sequence precedes already purged events and the client needs to reconstruct the current state. ChangeEvents are retained for approximately 14 days; current records preserve persistent state.

`since` accepts an ISO 8601 date and time with a timezone. Without `after_sequence`, the list returns the newest events first and `before_sequence` paginates backward. With `after_sequence`, pages are in ascending order. `project_id` limits results to a Project and its related records. The cursor is a global sequence per owner, not per Project. Project deletion permanently removes related events and advances the history-gap floor; clients with an earlier cursor rebuild current state. A generic `sync` signal contains no deleted Project identifier or name and does not appear in audit lists. The mobile event stream emits it as `event: sync` with empty data so clients refresh current state.

The owner can read histories by Project, Item or Entry and acknowledge specific events through `POST /v1/change-events/seen-batch` with their exact sequences. That endpoint only accepts owner credentials; agents cannot mark events as seen on the owner's behalf. Push and badges are derived from pending events and may change when they are acknowledged or retention expires.

In the app, recent Project, Item or Entry histories show auditable changes with local date and time. The view preserves visible changes during a refresh; opening another record loads its own history. Project activity identifies and shows its pending attention events first, even if they are older than already read changes; it then shows recent history. A pending goal proposal is labeled as such and opens its proposal. An Entry's history shows only its edits: if the first page includes creations that are not shown, it fetches older pages until it has five edits when they exist. The five most recent changes belonging to that view appear first; “Show more” reveals five additional changes each time and fetches older server pages when needed. Hidden changes are not marked as seen before they are visible on screen.

News collects only pending attention events, newest to oldest, with local date and time. It shows the five most recent notices; “Show more” reveals five additional notices each time and fetches older pages when needed. Showing or hiding notices does not change their read state; opening a destination fetches the current record before navigating.
