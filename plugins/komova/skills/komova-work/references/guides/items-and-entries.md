# Items and Entries

Items, Feed and Projects preserve visible content when returning from the lock screen or another app while fetching current data. Requests started before suspension do not replace the data or show late errors. An automatic read allows brief, bounded recovery if the connection fails temporarily; session, permission or data errors are not delayed. If the connection keeps failing, it shows an alert and allows a retry without discarding already loaded content. This recovery does not automatically retry saves or other owner actions.

`get_item` includes the Item's status, Forms and dependencies. `assigned_to_kind` identifies the current assignee (`human`, `agent` or null); `created_by_kind` identifies its author. `status` and `assigned_to_kind` are different fields. An agent Item in `needs_human` keeps its assignee while awaiting a human action. `waiting_on` is derived from incomplete prerequisites; `set_item_dependencies` replaces their UUIDs, requires the same owner and Project, and rejects cycles.

A human Item that blocks an agent Item in `needs_human` can be reassigned to `agent` with `change_item`: the same UUID is updated and the dependency is preserved. The dependent Item returns to `todo` only if there is no other pending human prerequisite; while the reassigned prerequisite remains incomplete, it remains in `waiting_on` and is not ready to execute. An unanswered required Form on the human Item prevents reassignment until it is completed; other conflicts retain their own errors.

When editing an Item, the app sends only changed fields through `PATCH /v1/items/{id}`; `scheduled_for=null` removes the date without altering other fields. If saving fails, it preserves the draft for a retry. It shows localized alerts based on the connection and HTTP response —session, permissions, missing record, invalid data, conflict or service failure— and does not show the server error details.

In the Item detail, Dependencies presents each prerequisite with the same outline and indicator as its card in List. The indicator is calculated from the current Item, including assignee, status, active work, date and pending prerequisites; it is not inferred solely from `needs_human`. The card opens that prerequisite.

The app allows deleting an Item from its detail after explicit confirmation. `DELETE /v1/items/{id}` accepts only the owner, returns `204` when it deletes the Item and `404` if the Item does not exist or belongs to another account; MCP does not offer a tool to delete it. Deletion removes its direct Forms, answers, Feedback and Reminders, along with the history and pending notices for that Item. A linked Entry remains in Feed but is no longer associated with the Item. The API rejects deletion with `409` if there are related dependents, still-pending human requests, goal proposals or active agent work. A historical human request allows deleting one endpoint when both Items are `done`; the other Item and its Forms are preserved. A historical incoming dependency also blocks deletion until the owner removes or reorganizes it. If the human Item is deleted, Komova preserves the idempotency key: retrying `request_human_action` or `request_information` returns a `human_action_deleted` conflict and does not recreate the action or reactivate the agent, even if that agent Item is reopened. A different action requires a new key; a concurrent request change may require refreshing and retrying deletion. After deletion, it emits `item/deleted` to refresh views and their read signals; a `404` retry must not be treated as a new confirmed deletion.

In the app, opening an Item notice fetches the current Item to verify that it belongs to the owner; if it has a Form with a pending required answer, it opens that exact Form directly, both on a cold app launch and from another tab. If no required answer remains pending, it opens the Item detail. The notice does not replace the fetch or contain the answers.

The mobile app keeps unsent answers as a local draft per Item, separated by user, Form and field, only on the device. When reopening the Form, it applies the draft only to compatible current fields that remain unanswered. Editing is quiet, without an alert for each local save; a failure to save the local draft is shown. It sends answers to the server only when the owner taps “Save answers” and then reports the result. For submitted answers and Item status, the server remains the source of truth: drafts are not available to agents through `get_item` or `get_information_request`.

List marks each Item as unread when it retains a previous read receipt (`seen=false`) or has pending attention events of its own or its descendants. The tab counter uses the same union. The global List shows current Items first, followed by collapsed groups in this order: Blocked, Scheduled and Done. Scheduled includes all future Items, read or unread; their read signals remain visible. Future Items also appear in their Project's Scheduled group. “Mark all as read” remains accessible while scrolling: it fetches a current list and acknowledges only the sequences represented by its Items, while also updating previous receipts with version checks. For this, List sends `acknowledge_direct_events=false` to `/v1/items/seen-batch` and then acknowledges exact sequences through `/v1/change-events/seen-batch`; the default `true` preserves installed clients' behavior. A concurrent change, later Feedback and events beyond the 100-sequence limit remain pending. If the counter reflects changes that loaded cards do not yet show, List refreshes the Items and counter to show the corresponding cards. An outdated counter with no pending Items does not generate an empty acknowledgement. Opening an Item acknowledges only its direct changes and previous receipt; Feedback is read separately.

`show_unseen_badge` is calculated by the API: for an Item it combines `seen=false` with its pending attention events; for an Entry it combines `read_at=null` with its events; for a Project it aggregates its own events and its children's events. The Feed counter counts each Entry marked this way once and adds unread Reminders. Completing a prerequisite updates its dependents' availability without creating a new notification for them or clearing previous notices. Editing a linked Entry announces the Entry in Feed and preserves the Item's previous read state.

`mark_agent_working` activates a visible working signal for 90 seconds and, if the agent Item was in `todo`, moves it to `doing` in the same operation. Another call renews the expiry without changing the status again. `stop_agent_working` deactivates the signal but leaves the Item in `doing`. Neither operation changes the assignee or dependencies. `scheduled_for` represents the Item's date, separate from these signals.

In the mobile app, the graphite theme uses a graphite background with a green tint and keeps the forest accent for actions and the active work signal. Cards and navigation maintain contrast with that background. The accents for news, attention, ready and blocked, as well as chosen Project colors, retain their distinctions. The theme does not change the status, assignee or read state of the Item: the working signal still depends on `doing` and a current lease.

`list_reports` and `get_report` read Entries with their sources; `add_report` and `change_report` create and edit an Entry. An Entry can link to only one Item, and each Item allows only one linked Entry. `body_markdown` contains the narrative; `sources` stores structured HTTPS links separately. `get_project_timeline` shows a Project's Entries and status transitions.

In Feed, the app splits a long Entry into horizontal pages with a character limit. It prefers breaks at line breaks and sentence endings, keeps indivisible Markdown fragments together, and uses the longest indivisible block as the basis for grouping short paragraphs that fit in one view. All pages share the same stable height, calculated from the tallest rendered Markdown page, without a height cap and without vertical scrolling inside the page. Feed scrolls vertically; tapping the post lets the owner open the full Entry. The detail preserves the complete content and its sources.

A Reminder is a separate, short card in Feed. The agent defines `text` (maximum 240 characters) and must specify the exact UUID of an owner's `project`, `item` or `entry`. Multiple Reminders can point to the same object; `idempotency_key` prevents duplicates on exact retries and rejects reuse with different content. It has no scheduled date. The owner marks it as read with `POST /v1/reminders/{id}/read`; the Feed counter adds unread Entries and Reminders. The destination is fetched again when opened; if it was deleted, the Reminder is deleted with it. If it points to an Item with a pending required Form, the app opens that exact Form. The agent's text is shown only in the authenticated app: the push preview uses bounded context and omits `text`.
